## Public API

- `TaskIdentifier.Compute(EvalTask, Model, ModelRoles?, EvalSetArgsInTaskIdentifier)` and `TaskIdentifier.Compute(EvalLog)` produce `{task}#{args_hash}/{model}/{additional_hash}` (a log's `task_file` prefix is honoured). `EvalSetArgsInTaskIdentifier.FromOptions(EvalOptions)` lifts the eval-level limits; `Config` is the eval model's generate config. `TaskIdentifier.Version` = 3. Cross-checked against Python's `task_identifier(read_eval_log(...), None)` on a log written by this runner (`EvalSetTests.task_identifier_matches_python_for_a_written_log`).
- `EvalSet.RunAsync(tasks, EvalSetOptions, ct)` → `EvalSetResult(Success, Logs)`. `EvalSetOptions`: `Eval` (the per-task `EvalOptions`, whose `LogDir` is the set's directory), `Models`, `RetryAttempts` (10), `RetryWait` (30 s, doubling, capped at 1 h), `RetryConnections` (1.0), `RetryCleanup` (true), `RetryImmediate` (true), `MaxTasks`, `LogDirAllowDirty`, `EvalSetId`, `Hooks`, `TimeProvider` (the batch-mode backoff clock). Complete tasks come back as headers (`Samples = null`); every task/model combination gets exactly one log.
- `EvalSetLogs` exposes the directory predicates individually; `EvalSetInfo.Read/Write/Build/EvalSetIdForLogDir` handle `eval-set.json` and `.eval-set-id`.
- `EvalSampleSource.FromLog(log, dataset, warn)` / `.Lookup(id, epoch)` / `.ErrorHistoryIds()` / `SeedErrorRetries` / `IsCancellationError`; set it on `EvalOptions.SampleSource` to resume a single `Eval.RunAsync` from a log (with `TaskId` and `InitialModelUsage` as `EvalSet`/`EvalRetry` do).
- `EvalRetry.RunAsync(logs | logPaths, EvalRetryOptions, ct)` → one new log per input, in order. The task comes from `Tasks` (name, then task-args hash) or `ResolveTask`; the model from `ResolveModel(spec)` (default `FoundryModels.Create(spec.Model, modelArgs: spec.ModelArgs)`), given the recorded `model_generate_config` with the `MaxRetries/Timeout/AttemptTimeout/StreamIdleTimeout/MaxConnections/AdaptiveConnections` overrides; roles from the recorded `model_roles` via `ResolveRoleModel`. Everything else (limits, epochs, sample selection, error policy, `max_samples`, sandbox cleanup) is read from the log unless overridden.
- Hooks: `EvalSet.RunAsync` notifies the registered `Hooks` (`HookRegistry`, plus `EvalOptions.Hooks` of `Eval`) of `OnEvalSetStartAsync` before any task runs and `OnEvalSetEndAsync` after the final status message (not when the run throws, as in Python), and runs the tasks of each pass under one hook run — one `run_id` shared by the pass's logs, one `RunStart` naming every task, task start/end per task (retries included), one `RunEnd` with the pass's logs (or the logs written so far and the exception when the pass throws) — as Python's `eval_set` calling `eval()` once per pass does. `IEvalSetHooks.OnEvalSetStartAsync/OnEvalSetEndAsync` (`EvalSetOptions.Hooks`) is an additional explicit seam notified after the registered hooks.

## Deviations from Python and why

- **No task registry or task files.** Identifiers of in-memory tasks have no `{task_file}@` prefix and their plan has no solver steps (solvers are delegates without registry names), so tasks differing only by solver must differ in name, `TaskArgs`, `Version` or config to be distinct; `model_args` are empty for in-memory models. `EvalRetry` therefore takes the tasks (and a model factory) explicitly and raises `PrerequisiteError` ("Task 'x' not found.") where Python raises `FileNotFoundError`.
- **Epoch reducers.** This runner always applies the task's reducers even when `EvalOptions.Epochs` overrides the count (Python drops them with a bare count), so the log records them and `ListLatestEvalLogs` folds Python's eval-level `epochs_changed` check into `LogSamplesComplete`, which compares against the task's reducer names. A retried log's epochs count comes from the log, its reducers from the task.
- **Sample shuffle** is not ported, so `shuffle_changed` compares a null request against the log.
- **Logs are read whole** (both `.eval` and `.json`, through the format-aware `EvalLogWriter` of the eval-format port): no sample summaries, no recorder buffer — the reuse "flush" and "deferred destination log" designs reduce to writing the finished log once, and a crashed `started` log is not recovered (it is treated as incomplete and re-run; its samples are not reusable). The carry-forward of error history runs at finish from the in-memory results.
- **Latest-log ordering** breaks an mtime tie (attempts within one filesystem timestamp tick) on the log's completion time; Python sorts by mtime alone but bumps the retry's timestamp instead.
- **Dispatcher.** A configuration exception escaping `Eval.RunAsync` (e.g. a cost limit without cost data) stops the set and propagates; Python converts a log-write failure into an errored log and retries it. Cancellation propagates as `OperationCanceledException` after the tasks in flight have written their cancelled logs.
- **`retry_connections`** decays every model's `MaxConnections` (Python injects a single `max_connections` kwarg); it is forced to 1.0 when adaptive connections are active, as in Python.
- **`EvalRetry`** runs logs sequentially (Python too, per log), defaults `LogDir` to the log's own directory (Python: `./logs`), and — like Python — writes the retried log without an `eval_set_id`; only the overrides listed above are honoured (no `log_*`, `score`, `debug_errors`, ACP/ctl/scanner/checkpoint options). The log's `eval.config.approval` is re-installed as the eval-level policy, as `eval_retry_async` does, so a retried sample runs under the same tool-approval gate.
- Reused samples are reported to `IEarlyStopping.CompleteSampleAsync` (as Python does) but never to `ScheduleSampleAsync`.

## Not ported

`write_log_dir_manifest`, `bundle_dir`, `embed_viewer`, the control server / keep-alive park / launch handoff, scanners, checkpoints, `TaskSource`/`SampleSource` feeds, early task pruning and selection mode, `EvalSetOverrides`, ACP/notification/approval settings, `read_eval_log_sample_summaries`, `resolved_model_names`, `ModelList`.

## Update (showcase-wiring)

The `.eval` recorder writes samples incrementally, so "writing the finished log once" no longer covers reuse: the
runner now re-logs a reused sample (and a carried-forward errored one) into the retry's log as Python's reuse sweep
and `carry_forward_unlogged_samples` do, and records `eval.dataset.samples` as the whole dataset size (Python's
`len(task.dataset)`) so a `--limit` run can be resumed. See `docs/ports/showcase-wiring.md`.
