# Sandbox and container orchestration: C# port vs Python inspect_ai

> Snapshot 2026-09-10: this repo at `main` 58b8585, inspect_ai at 76f1aa761. Produced by a multi-agent parity audit (see [Method](#method)). Evidence is cited as `py:<path>:<line>` for inspect_ai and `cs:<path>:<line>` for this repo, with line numbers as of those commits.

## Summary

The C# port is **not at full parity, but it is close for the common case.** The core lifecycle is a faithful port: task init, sample init, file copy and setup, the `Sandbox()` accessors, exec/read/write, and cleanup. So are the compose up/wait/default-service/down loop, tool-support injection with its chunked JSON-RPC transport, and `SandboxService`. Single-service and simple multi-service compose tasks with an explicit config path, the standard bash/python/text_editor tools, and the human agent behave as they do in Python.

The differences show up with default settings, compose files that use advanced YAML, agents in network-isolated containers, and runs at scale:

- **The default mode drops network isolation.** `INSPECT_DOCKER_COMPOSE=auto` runs images, Dockerfiles and empty configs as a plain `docker run` with network access; Python always uses compose with `network_mode: none`.
- **Sandbox configs are not resolved against the task directory**, and `eval-retry` ignores the logged sandbox spec.
- **Compose files are parsed by the hand-rolled MiniYaml**, not `docker compose config`: anchors, merge keys, tags, `${VAR}` interpolation, profiles, `extends` and `include` are unsupported.
- **Parallel eval-set runs of one task can tear down each other's containers**, because compose projects are tracked by task name in one shared provider.
- **There is no `max_sandboxes` limit, no `exec_remote`, and the agent bridge needs a network path to the host.**
- **Per-sample init environments, internal images and `--sandbox-prebuilt` are missing.**

> **Workaround for the biggest risk:** set `INSPECT_DOCKER_COMPOSE=always` so images, Dockerfiles and empty configs go through compose with `network_mode: none`, as in Python. Agents that use the sandbox agent bridge then cannot reach the host listener, so this trades isolation against bridge access until the bridge moves into the container.

## How a sandboxed eval runs

### Python

1. Register and look up the provider. SandboxEnvironment subclasses register with @sandboxenv. Lookup is an exact unqualified-name match; on a miss it loads the 'inspect_ai' entry points, and if still missing it raises with an install hint for k8s/ec2/proxmox/modal/daytona (`py:src/inspect_ai/util/_sandbox/registry.py:24-68`; `py:src/inspect_ai/_util/registry.py:324`).
2. Normalise specs. The str/tuple, CLI type:config and dataset shorthands become SandboxEnvironmentSpec(type, config), where config is a path or a pydantic model; a dict becomes a ComposeConfig for docker-compatible providers. Dataset loaders resolve sample sandbox, files and setup paths against the dataset directory (`py:src/inspect_ai/util/_sandbox/environment.py:542-627`; `py:src/inspect_ai/dataset/_sources/util.py:47-70`).
3. Resolve the task sandbox. The eval/eval_set/CLI sandbox argument replaces task.sandbox. The provider's config_files() (compose.yaml, Dockerfile) are looked for in the task directory. A docker-compatible task config is carried over (with a warn_once otherwise), and relative paths become absolute against the task directory. eval_retry reuses the logged spec, resolved relative to the logged task_file (`py:src/inspect_ai/_eval/loader.py:391-453`).
4. Start sandboxes once per run. SandboxManager.start resolves each sample: the task type wins, and the sample config applies on a same-type or docker-compatible match, otherwise it warns once. It gathers task_init_environment env vars (Docker runs `compose config --images` with SAMPLE_METADATA\_\*) and dedupes (spec, run_dir, env) across all tasks. Under \_init_lock it registers the sandboxes/&lt;type> limiter and runs task_init('startup') under chdir(run_dir) (`py:src/inspect_ai/_eval/task/sandbox.py:249-329`; `py:src/inspect_ai/_eval/run.py:1003-1053`).
5. Docker task_init. It runs validate_prereqs (Engine >= 24.0.6, Compose >= 2.21) and resolves the compose file: an explicit path, an auto-compose wrapper for a Dockerfile, a ComposeConfig, or the default aisiuk/inspect-tool-support service with network_mode: none. It reads services from `docker compose config`, builds (or verifies prebuilt images), rejects container_name, builds internal images and pulls missing ones (`py:src/inspect_ai/util/_sandbox/docker/docker.py:86-156`; `py:src/inspect_ai/util/_sandbox/docker/prereqs.py:23-110`; `py:src/inspect_ai/util/_sandbox/docker/config.py:113-133`).
6. Gate the sample. sandboxenv_context sleeps a random jitter, then holds the sandboxes/&lt;type> semaphore (max_sandboxes, else default_concurrency: 2x effective CPUs for Docker) for the sandbox's whole life. It reads Sample.files (data URIs, http with retries, fsspec, directories, inline text) and the setup script (`py:src/inspect_ai/_eval/task/sandbox.py:51-143,181-240`).
7. Docker sample_init. It creates the project inspect-&lt;slug12>-i<6> with SAMPLE_METADATA\_\* env and runs `compose up --detach --wait --wait-timeout`, sized from the healthchecks. Every service must be running or exited 0. Each running service becomes an environment, with the default (x-default, else 'default', else an error) first. Any failure brings the project down (`py:src/inspect_ai/util/_sandbox/docker/docker.py:191-267`; `py:src/inspect_ai/util/_sandbox/docker/compose.py:34-60,118-134`).
8. Per-sample setup. Environments are wrapped in SandboxEnvironmentProxy (SandboxEvents, TimeoutError mapped to SandboxTimeoutError, output cap), context vars are set, files are copied with 'envname:' routing, and setup runs from /tmp under INSPECT_SANDBOX_SETUP_TIMEOUT. On failure it calls sample_cleanup(interrupted=True), which Docker defers to task_cleanup. It then publishes sandbox_connections and starts working time (`py:src/inspect_ai/util/_sandbox/context.py:251-292`; `py:src/inspect_ai/util/_sandbox/events.py:33-138`; `py:src/inspect_ai/_eval/task/run.py:2446-2458`).
9. Solver, tools and scorers. Code uses sandbox()/sandbox_with/sandbox_default. Tools inject sandbox-tools with sandbox_with_injected_tools and call its JSON-RPC server with one exec per call, plus chunking. Docker exec is `compose exec ... timeout -k 5s` with a +10s host guard, a retry on host hangs, classify_exec_failure, and post-mortem diagnostics when the service is dead (`py:src/inspect_ai/util/_sandbox/context.py:42-172`; `py:src/inspect_ai/tool/_sandbox_tools_utils/sandbox.py:75-143`; `py:src/inspect_ai/util/_sandbox/docker/docker.py:309-446`).
10. Long-running work. exec_remote starts streaming, killable background processes on the in-container server. sandbox_service provides file-based RPC back to the host. The agent bridge runs model_proxy inside the container on top of that service, so it works under network_mode: none (`py:src/inspect_ai/util/_sandbox/exec_remote.py:191-648`; `py:src/inspect_ai/util/_sandbox/service.py:105-213`; `py:src/inspect_ai/agent/_bridge/sandbox/bridge.py:136-232`).
11. Sample end. Task.cleanup runs while the sandboxes are still up. sample_cleanup runs only when cleanup is enabled, and is shielded and flagged when the sample was interrupted. Docker runs `compose down --volumes` plus image cleanup, or defers interrupted samples. A cleanup exception becomes the sample's error (`py:src/inspect_ai/_eval/task/run.py:2849-2861`; `py:src/inspect_ai/_eval/task/sandbox.py:164-178`; `py:src/inspect_ai/util/_sandbox/docker/docker.py:271-290`).
12. Run shutdown. SandboxManager.shutdown calls each recorded task_cleanup('shutdown', config, cleanup) once, shielded, under chdir(run_dir). Docker brings leftover projects down in parallel, or prints a Sample/Epoch/Containers table with `inspect sandbox cleanup docker` commands, then removes the auto-compose files (`py:src/inspect_ai/_eval/run.py:1060-1070`; `py:src/inspect_ai/util/_sandbox/docker/cleanup.py:72-114`).
13. Out-of-band recovery. `inspect sandbox cleanup TYPE [ID]` calls cli_cleanup. For Docker that lists inspect projects with `compose ls --all`, brings them down and sweeps orphaned auto-compose files (`py:src/inspect_ai/_cli/sandbox.py:17-30`; `py:src/inspect_ai/util/_sandbox/docker/cleanup.py:141-173`).

### C#

1. Register and look up the provider. SandboxRegistry is a static, case-insensitive dictionary pre-seeded with local and docker. Any other provider must call Register in code, and Get throws with a list of the known types. **Differs:** no entry-point or assembly discovery, no install hints, and names match case-insensitively (`cs:src/InspectAzureAI.Eval/Sandbox/SandboxRegistry.cs:15-47`).
2. Normalise specs. A spec is SandboxSpec(Type, string? Config). CLI type:config and dataset string or [type, config] parse as in Python, and dataset loading resolves sample config, files and setup paths against the dataset file. **Differs:** no object or ComposeConfig configs, and object configs in logs are rejected (`cs:src/InspectAzureAI.Eval/Sandbox/SandboxSpec.cs:9`; `cs:src/InspectAzureAI.Eval/Dataset/SampleRecords.cs:43-71,224`).
3. Resolve the task sandbox. The only override is the CLI's --sandbox, which overwrites EvalTask.Sandbox in Plan.Build. **Differs:** no library-level override, no config_files discovery, no config carry-over, relative paths resolved against the process cwd, and EvalRetry ignores the logged spec (`cs:src/InspectAzureAI.Cli/Commands/EvalCommands.cs:593,659-661`; `cs:src/InspectAzureAI.Eval/Runner/EvalSet/EvalRetry.cs:120-155`).
4. Start sandboxes per task. Eval.RunAsync starts the log and runs ResolveSpec for each sample; the sample config applies only when the types match case-insensitively, and there is no warning. It takes the distinct specs and awaits TaskInitAsync(task.Name, config) for each before samples start; a failure becomes that task's Error log. **Differs:** per task rather than per run, no chdir, no task_init_environment, no limiter. EvalSet dispatches several (task, model) runs at once, so tasks sharing a config init it concurrently (`cs:src/InspectAzureAI.Eval/Runner/Eval.cs:179-236`; `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:25-37`; `cs:src/InspectAzureAI.Eval/Runner/EvalSet/EvalSet.cs:303-307,376`).
5. Docker task_init. INSPECT_DOCKER_COMPOSE=auto sends compose-shaped configs to DockerComposeSandbox, which resolves the file (ported auto-compose templates), parses it with MiniYaml, runs compose build and image cleanup, rejects container_name and pulls missing images. Images, Dockerfiles and null configs with no compose file in the cwd go to DockerImages.EnsureAsync instead: a content-hash build or a pull, defaulting to python:3.12-slim-bookworm. **Differs:** bare docker is the default for non-compose configs, services are not read through `compose config`, and there are no prerequisite checks, prebuilt mode or internal images (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxProvider.cs:67-134`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:27-75`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerImages.cs:14-83`).
6. Gate the sample. Concurrency is limited only by SampleScheduler (MaxSamples or adaptive connections). SandboxSetup reads files and setup synchronously from data URIs, local files, directories or inline text. **Differs:** no max_sandboxes or default_concurrency semaphore and no jitter; http and fsspec values are written into the sandbox as literal text (`cs:src/InspectAzureAI.Eval/Runner/Eval.cs:203`; `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:85-127`).
7. Docker sample_init. The compose path creates a fresh project with SAMPLE_METADATA\_\* env and runs `compose up --detach --wait --wait-timeout` with Python's healthcheck formula. It checks the running and exited-0 containers against the service count from the raw file, and makes each running container an environment (WorkingDir from docker inspect), default first: x-default, then 'default', then a lone service. The bare path runs `docker run -d --init --add-host host.docker.internal:host-gateway IMAGE sleep infinity` on the default bridge network. **Differs:** profile-gated services break the count, and bare containers have network access (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:84-143`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeCli.cs:56-63,195-207`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerCli.cs:25-31`).
8. Per-sample setup. SampleRunner opens the init span. SandboxSetup.InitAsync converts metadata to strings and adds \_\_sample_id\_\_, calls SampleInitAsync, copies files with 'envname:' routing, and runs setup under INSPECT_SANDBOX_SETUP_TIMEOUT; working time starts after the span closes. **Differs:** there is no proxy, so no SandboxEvents and no timeout normalisation, and no sandbox_connections. A setup failure calls Cleanup(true), which removes the containers at once even under --no-sandbox-cleanup (`cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:40-79`; `cs:src/InspectAzureAI.Eval/Runner/SampleRunner.cs:124-145`).
9. Solver, tools and scorers. Code uses SampleContext.Sandbox(name) over AsyncLocal (the first entry is always the default), SandboxWith.FindAsync, and SandboxToolSupport injection over the ported JSON-RPC transport with chunking. Compose exec runs through bare `docker exec CONTAINER` wrapped in `timeout -s KILL`, with a +10s host guard and no retry, DockerFailures classification and no diagnostics. **Differs:** no sandbox_default, no exec timeout_retry or concurrency flags, and read_file is `cat` with no timeout (`cs:src/InspectAzureAI.Eval/Context/SampleContext.cs:54-72`; `cs:src/InspectAzureAI.Eval/Tools/Support/SandboxToolSupport.cs:74-220`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxEnvironment.cs:123-294`).
10. Long-running work. **Differs:** there is no exec_remote. SandboxService ports the file-based RPC, but only the human agent uses it. The agent bridge is a host HttpListener protected by a token and reached at host.docker.internal. Scaffolds such as Claude Code run as one blocking ExecAsync that limit and terminate tokens cancel (`cs:src/InspectAzureAI.Eval/Sandbox/SandboxService.cs:155-212`; `cs:src/InspectAzureAI.Eval/Agents/Bridge/SandboxAgentBridge.cs:79-121`; `cs:src/InspectAzureAI.Swe/ClaudeCode/ClaudeCodeAgent.cs:251-278`).
11. Sample end. Scoring runs with the sandboxes still up, then a finally block always calls Cleanup(options.Cleanup). Compose runs `down --volumes` plus image cleanup inline with CancellationToken.None, or logs a kept-for-inspection hint; bare docker runs `rm -f` or keeps the container. **Differs:** no Task.cleanup hook, no interrupted flag, and a cleanup exception is only an ErrorEvent (`cs:src/InspectAzureAI.Eval/Runner/SampleRunner.cs:215,250-263`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:194-216`).
12. Task end. A finally block calls TaskCleanupAsync with CancellationToken.None for every distinct spec, including specs never initialised. Compose brings down or lists every running project tracked under that task name and deletes that task's auto-compose files; errors go only to the optional reporter. **Differs:** cleanup runs per task and is keyed by task name, so concurrent runs of the same task share one project list (`cs:src/InspectAzureAI.Eval/Runner/Eval.cs:237-251`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:151-164,218-262`).
13. Out-of-band recovery. **Missing:** ISandboxProvider has no cli_cleanup member and the CLI registers no sandbox command group. Kept or leaked projects must be removed by hand with the logged `docker compose --project-name <name> down --volumes` (`cs:src/InspectAzureAI.Eval/Sandbox/ISandboxProvider.cs:8-21`; `cs:src/InspectAzureAI.Cli/InspectCli.cs:38-46`).

## Biggest gaps

Ranked by (1) whether an existing inspect_ai task or compose file fails or behaves differently in C#, (2) reliability: leaked containers, hangs, unclear failures, (3) extensibility for other providers, and (4) developer ergonomics.

### 1. The default mode drops network isolation (high)

The default docker routing changes isolation and the default image. Under INSPECT_DOCKER_COMPOSE=auto, a Dockerfile, image or empty docker config runs as a bare `docker run` container on the default bridge network, with internet access and host.docker.internal, using python:3.12-slim-bookworm when there is no config. Python always wraps these in auto-compose with network_mode: none and aisiuk/inspect-tool-support. A `Dockerfile.<name>` config is also misread as an image reference and pulled.

**Why it matters:** Every Dockerfile or image-based task gets network access that Python withholds, so an agent can reach the internet or the host during an eval meant to be offline. That silently changes results and weakens containment. Setting INSPECT_DOCKER_COMPOSE=always restores Python's behaviour, but it is not the default.

- **Python:** `py:src/inspect_ai/util/_sandbox/docker/config.py:113-133`; `py:src/inspect_ai/util/_sandbox/docker/util.py:61-75`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxProvider.cs:127-134`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerCli.cs:25-31`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerImages.cs:14,25-53`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeProject.cs:311-314`

### 2. Sandbox configs are not resolved against the task directory (high)

resolve_task_sandbox is not ported. A null config never finds a compose.yaml or Dockerfile next to the task; it only looks for a compose file in the process cwd. Relative config paths resolve against the cwd. --sandbox replaces the spec without carry-over, EvalOptions and EvalSetOptions have no sandbox override, and eval-retry ignores the logged sandbox spec.

**Why it matters:** A ported task declaring sandbox="docker" with a compose file or Dockerfile beside it silently gets the default image unless it is run from that directory. Retrying a run that used --sandbox falls back to the task's default sandbox. The ported examples only work because they hard-code compose paths.

- **Python:** `py:src/inspect_ai/_eval/loader.py:391-453`; `py:src/inspect_ai/_eval/eval.py:1701-1711`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeProject.cs:296-302`; `cs:src/InspectAzureAI.Cli/Commands/EvalCommands.cs:659-661`; `cs:src/InspectAzureAI.Eval/Runner/EvalSet/EvalRetry.cs:120-155`

### 3. Compose files are parsed by MiniYaml, not docker compose config (high)

Compose files are parsed raw by the in-process MiniYaml instead of `docker compose config`. Anchors, aliases, merge keys, tags (including !reset/!override) and multi-line quoted strings in block context throw. \${VAR} interpolation, profiles, extends and include are not applied before the provider reads the service list.

**Why it matters:** Valid compose files that work in Python fail in C#. An `x-common: &common` anchor throws. A profile-gated service triggers 'No services started'. An include-only file 'defines no services'. A \${VAR} healthcheck duration throws FormatException, and a \${SAMPLE_METADATA_IMAGE} image fails the local-image check. No test runs real compose, so none of this is exercised.

- **Python:** `py:src/inspect_ai/util/_sandbox/docker/compose.py:118-134,264-268`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeConfig.cs:79-144`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/MiniYaml.cs:399-409,517-519,546`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeCli.cs:195-207`

### 4. No per-sample init environment, internal images or prebuilt mode (high)

Docker task_init is missing task_init_environment (a separate init per distinct metadata env, with SAMPLE_METADATA\_\* set), internal image builds (inspect_web_browser, inspect-computer-tool) and --sandbox-prebuilt verification.

**Why it matters:** Compose files that choose per-sample images from metadata (the SWE-bench style) are built and pulled with blank variables, so they get the wrong image or fail validation. Services using internal inspect images fail to pull. Air-gapped runs that rely on verifying prebuilt images have no equivalent.

- **Python:** `py:src/inspect_ai/util/_sandbox/docker/docker.py:104-187`; `py:src/inspect_ai/util/_sandbox/docker/internal.py:6-48`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/ISandboxProvider.cs:14`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:14-16,27-68`

### 5. No exec_remote, and the agent bridge needs host networking (high)

exec_remote does not exist: no streaming, stdin, kill or background jobs, and no bash(background=True). The sandbox agent bridge is a host HttpListener reached at host.docker.internal rather than an in-container model_proxy over file RPC. Only bare `docker run` maps that hostname, and only the Anthropic messages and chat-completions routes are served.

**Why it matters:** Agent scaffolds cannot run in network_mode: none compose sandboxes, or in compose services on Linux without extra_hosts, which is where offline agent evals normally run; Python's bridge works there. Long jobs block a single exec and return only the tail of their output, and tasks or tools built on exec_remote cannot be ported.

- **Python:** `py:src/inspect_ai/util/_sandbox/exec_remote.py:191-648`; `py:src/inspect_ai/agent/_bridge/sandbox/bridge.py:136-299`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/ISandboxEnvironment.cs:18-25`; `cs:src/InspectAzureAI.Eval/Agents/Bridge/SandboxAgentBridge.cs:79-121,306`; `cs:src/InspectAzureAI.Swe/ClaudeCode/ClaudeCodeAgent.cs:251-278`

### 6. No max_sandboxes limit (high)

There is no sandbox concurrency limiter: no max_sandboxes or default_concurrency semaphore (Docker's default is 2x effective CPUs), no --max-sandboxes, and no global subprocess limiter. The docker-CLI gate covers compose management commands only, not DockerCli run/exec/cp.

**Why it matters:** The number of live containers is bounded only by max_samples or adaptive connections (the limit plus 5), not by host CPUs. Large evals can oversubscribe Docker and produce timeouts, OOM kills and spurious sample errors that Python's defaults avoid, and eval-set multiplies this across parallel tasks.

- **Python:** `py:src/inspect_ai/_eval/task/sandbox.py:51-128`; `py:src/inspect_ai/util/_sandbox/docker/docker.py:78-83`; `py:src/inspect_ai/util/_subprocess.py:220-253`
- **C#:** `cs:src/InspectAzureAI.Eval/Runner/Eval.cs:203`; `cs:src/InspectAzureAI.Eval/Concurrency/DynamicSampleLimiter.cs:15,37`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeCli.cs:40-44,345-366`

### 7. Projects are tracked by task name, and there is no cleanup CLI (high)

The single shared DockerComposeSandbox tracks running projects and auto-compose files by task name and cleans up per task, while EvalSet runs up to maxTasks (task, model) pairs at once. There is also no `inspect sandbox cleanup` command, no `compose ls` recovery and no sweep of orphaned auto-compose files.

**Why it matters:** When one task runs against two models, whichever run finishes first brings down (or just lists) the other run's live sample projects and deletes auto-compose files that run still needs, killing samples mid-run. Containers left behind by a crash, SIGTERM or --no-sandbox-cleanup have to be found and removed by hand.

- **Python:** `py:src/inspect_ai/util/_sandbox/docker/cleanup.py:21-24,50-173`; `py:src/inspect_ai/_cli/sandbox.py:17-30`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:22-24,158-164,218-262`; `cs:src/InspectAzureAI.Eval/Runner/EvalSet/EvalSet.cs:303-307,376`; `cs:src/InspectAzureAI.Eval/Sandbox/ISandboxProvider.cs:8-21`

### 8. MCP servers in the sandbox skip injection and chunking (medium)

McpServerSandbox uses SampleContext.Sandbox(name) without injecting tool support. Its carrier never sets INSPECT_SANDBOX_JSON_RPC_RESPONSE_MAX_BYTES and never reassembles chunked responses.

**Why it matters:** A sandbox MCP server fails to launch unless another tool has already injected the CLI. Any response over the in-container default of 64 KiB arrives as a chunk envelope the carrier cannot use, which breaks ordinary results such as file listings or page content.

- **Python:** `py:src/inspect_ai/tool/_mcp/_sandbox.py:55-214`; `py:src/inspect_ai/util/_sandbox/_json_rpc_transport.py:63-213`
- **C#:** `cs:src/InspectAzureAI.Eval/Tools/Mcp/Mcp.cs:99-123`; `cs:src/InspectAzureAI.Eval/Tools/Mcp/McpSandboxTransport.cs:54-120`

### 9. Remote Sample.files are never fetched (medium)

Sample.files and setup values that are http(s) URLs or fsspec paths are never fetched.

**Why it matters:** When a dataset points files at remote URLs, the URL string itself is written into the container as the file's contents. The sample runs on the wrong inputs with no error.

- **Python:** `py:src/inspect_ai/_eval/task/sandbox.py:181-240,332-357`
- **C#:** `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:85-127`

### 10. No SandboxEvents or timeout normalisation (medium)

There is no SandboxEnvironmentProxy. exec, read_file and write_file record no SandboxEvent, a provider's TimeoutException is not normalised to SandboxTimeoutException, and sandbox_connections are not published on the active sample.

**Why it matters:** C# transcripts do not show which commands ran in the container, their exit codes or their output. Logs cannot be compared with Python's in the viewer, and sandbox-heavy samples cannot be audited. A third-party provider's plain TimeoutException also skips the 'timeout' tool-error mapping.

- **Python:** `py:src/inspect_ai/util/_sandbox/events.py:33-255`; `py:src/inspect_ai/util/_sandbox/context.py:227-270`
- **C#:** `cs:src/InspectAzureAI.Eval/Log/Json/TranscriptEventConverter.cs:39`; `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:40-79`

### 11. Failures are unclear and some operations can hang (medium)

Several gaps make failures unclear and allow hangs:

- no Docker Engine or Compose version check;
- no post-mortem diagnostics for a dead container (ps --all, .State with OOMKilled, logs --tail);
- build and pull output hidden unless they fail;
- no subprocess trace log;
- read_file runs `cat` with no timeout;
- an exec that hangs on the host is never retried;
- sandbox PrerequisiteErrors land in an Error log (exit 1) instead of the CLI's prerequisite handler.

**Why it matters:** An old Docker fails later on a missing flag with no upgrade guidance, and an OOM-killed container shows only 'sandbox unavailable'. Long builds look like a hang. A read on a FIFO or a stuck filesystem blocks the sample until the whole sample is cancelled.

- **Python:** `py:src/inspect_ai/util/_sandbox/docker/prereqs.py:23-110`; `py:src/inspect_ai/util/_sandbox/docker/diagnostics.py:36-145`; `py:src/inspect_ai/util/_sandbox/docker/docker.py:536-545`; `py:src/inspect_ai/util/_subprocess.py:238`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxEnvironment.cs:123-149,249-294`; `cs:src/InspectAzureAI.Eval/Runner/Eval.cs:230-236`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeCli.cs:132-148`

### 12. The provider model is narrower (medium)

The provider model is narrower:

- SandboxSpec.Config is string-only, so no ComposeConfig or provider config objects;
- ISandboxProvider has no config_files, is_docker_compatible, default_concurrency, polling-interval, task_init_environment, cli_cleanup or interrupted hooks;
- providers are registered in code only, with no entry-point or assembly discovery and no CLI hook;
- only local and docker exist (no k8s, cloud or Azure provider);
- there is no reusable self_check conformance suite.

**Why it matters:** A Kubernetes, Azure Container Apps or other remote provider cannot declare Docker compatibility, its concurrency, per-sample images or deferred cleanup after an interruption. It cannot be selected from the inspectai CLI without a custom host, and nothing checks it for behavioural parity with the built-in providers.

- **Python:** `py:src/inspect_ai/util/_sandbox/environment.py:127-627`; `py:src/inspect_ai/_util/registry.py:319-326`; `py:src/inspect_ai/util/_sandbox/self_check.py:1-25`
- **C#:** `cs:src/InspectAzureAI.Eval/Sandbox/ISandboxProvider.cs:8-21`; `cs:src/InspectAzureAI.Eval/Sandbox/SandboxSpec.cs:9`; `cs:src/InspectAzureAI.Eval/Sandbox/SandboxRegistry.cs:15-43`; `cs:src/InspectAzureAI.Eval/Sandbox/SandboxService.cs:211-212`

## Deliberate differences in mechanism

### Sample cleanup hook and the meaning of its bool

- **Python:** sample_cleanup(task_name, config, environments, interrupted) is a classmethod that is skipped entirely when cleanup is disabled. Docker defers interrupted and setup-failed samples to task_cleanup (`py:src/inspect_ai/_eval/task/sandbox.py:164-178`; `py:src/inspect_ai/util/_sandbox/docker/docker.py:271-290`).
- **C#:** SampleInitAsync returns a Func&lt;bool,Task> closure, always called with the cleanup-enabled flag. A setup failure calls Cleanup(true), which runs compose down or rm -f immediately (`cs:src/InspectAzureAI.Eval/Sandbox/SandboxEnvironments.cs:9`; `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:70-77`; `cs:src/InspectAzureAI.Eval/Runner/SampleRunner.cs:250-263`).
- **Assessment:** Risk. The closure is a reasonable .NET shape, but dropping 'interrupted' changes behaviour. With --no-sandbox-cleanup, a container whose setup script failed is destroyed in C#, while Python keeps and lists it, and that is exactly the container a user wants to inspect. The ecosystem table's 'parity' verdict on this row is wrong; checked against docker.`py:280-290`.

### Scope of task_init / task_cleanup

- **Python:** Runs once per unique (spec, run_dir, env) across the whole run, under a lock, with the names 'startup' and 'shutdown' and chdir(run_dir) (`py:src/inspect_ai/_eval/run.py:1003-1070`).
- **C#:** Runs per EvalTask inside Eval.RunAsync, with task.Name and no chdir or env. EvalSet runs tasks in parallel, and cleanup also runs for specs that were never initialised (`cs:src/InspectAzureAI.Eval/Runner/Eval.cs:179-251`).
- **Assessment:** Risk. It fits eval-set's per-task isolation, since a failed init errors one task rather than the whole run. But it repeats builds and pulls, runs compose builds for shared files in parallel, and together with task-name tracking lets concurrent runs of one task tear down each other's projects.

### Always-compose vs bare single-container mode

- **Python:** Every docker config goes through docker compose. An image, a Dockerfile or no config is wrapped in an auto-compose file with network_mode: none (`py:src/inspect_ai/util/_sandbox/docker/util.py:31-83`).
- **C#:** INSPECT_DOCKER_COMPOSE=auto routes only compose-shaped configs to compose. Images, Dockerfiles and null configs with no compose file use `docker run -d --init --add-host host.docker.internal:host-gateway` (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxProvider.cs:127-134`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerCli.cs:25-31`).
- **Assessment:** Risk as a default. It removes the dependency on the compose plugin and lets the host-side agent bridge work, but it silently changes network isolation and the default image. It would be fine as an opt-in mode, with 'always' as the default.

### How services are enumerated

- **Python:** From `docker compose config` output, which is interpolated, merged and profile-filtered (`py:src/inspect_ai/util/_sandbox/docker/compose.py:264-268`).
- **C#:** From a MiniYaml parse of the raw file; the compose CLI still receives the original file via -f (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeConfig.cs:79-144`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/ComposeCli.cs:308`).
- **Assessment:** Risk. It saves one subprocess, but the provider's view of the services can disagree with what compose actually starts: the running count, pulls, healthcheck wait and default selection. Reading `compose config --format json` would close most of the compose-file gap, or at least falling back to it on NotSupportedException.

### Exec transport for compose services

- **Python:** `docker compose exec SERVICE`, run through compose_command with the docker-cli gate, the subprocess limiter and a broken-pipe retry (`py:src/inspect_ai/util/_sandbox/docker/docker.py:309-429`).
- **C#:** `docker exec CONTAINER`, bound to the container name captured at sample init and bypassing the CLI gate (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandboxEnvironment.cs:44-64`).
- **Assessment:** Mostly fine, and faster, because it skips compose's per-call config read. The costs are that exec is not throttled, and the failure classifier matches daemon messages that Python deliberately ignores because a model inside a docker-in-docker sandbox could print them.

### Read_file transport

- **Python:** compose cp -L to a host temp file with a 600s timeout and a canary check, then a size check (`py:src/inspect_ai/util/_sandbox/docker/docker.py:513-591`).
- **C#:** exec `cat` with no timeout, killed once output passes the size limit (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxEnvironment.cs:123-168`).
- **Assessment:** Risk. It avoids staging files on the host and stops oversize reads early. But it needs `cat` in the image, reads with the container user's permissions (docker cp ignores them), cannot detect non-regular files, and can hang on a FIFO. It should at least have a timeout.

### In-container timeout signal

- **Python:** `timeout -k 5s Ns`: SIGTERM, then SIGKILL 5s later, exiting 124 (`py:src/inspect_ai/util/_sandbox/docker/docker.py:346-357`).
- **C#:** `timeout -s KILL Ns`, whose exit 137 is classified by elapsed time; on host cancel, ProcessRunner kills the process tree at once (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxEnvironment.cs:220-260`; `cs:src/InspectAzureAI.Eval/Sandbox/Docker/ProcessRunner.cs:83,167`).
- **Assessment:** Low risk. Timeouts are still reported correctly, but commands get no graceful shutdown (temp files, child servers, log flushes), and the docker CLI gets no SIGTERM window when the host cancels.

### Passing env vars to exec

- **Python:** `--env K=V` in argv (`py:src/inspect_ai/util/_sandbox/docker/docker.py:337-340`).
- **C#:** `-e K`, with the value set in the docker CLI's process environment (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerCli.cs:63-83`).
- **Assessment:** Fine, and an improvement: the container sees the same values, and secrets stay out of the host process list.

### Working directory detection

- **Python:** `compose exec SERVICE sh -c pwd` (`py:src/inspect_ai/util/_sandbox/docker/docker.py:689-702`).
- **C#:** `docker inspect {{.Config.WorkingDir}}`, with an empty value mapped to '/' (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:278-289`).
- **Assessment:** Fine: same result, and it also works in images that have no sh.

### Escalating silent signal exits

- **Python:** A silent exit above 128 is escalated only when `compose ps --all` shows every container exited or dead; a failed probe counts as alive (`py:src/inspect_ai/util/_sandbox/docker/docker.py:409-422`).
- **C#:** It is escalated when .State.Running is not true, or when docker inspect fails or times out (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/DockerSandboxEnvironment.cs:263-294`).
- **Assessment:** Minor risk. Under daemon load a slow or failing inspect turns an ordinary signal exit into SandboxUnavailable, which ends the sample instead of returning a tool result.

### Agent bridge transport

- **Python:** model_proxy runs inside the container (SANDBOX_CLI model_proxy via exec_remote), serves OpenAI, Anthropic, Google and MCP on localhost, and reaches the host through sandbox_service file RPC (`py:src/inspect_ai/agent/_bridge/sandbox/bridge.py:136-299`).
- **C#:** A host HttpListener with a per-instance token, bound to 127.0.0.1 for local sandboxes and to all interfaces for Docker, reached at host.docker.internal (`cs:src/InspectAzureAI.Eval/Agents/Bridge/SandboxAgentBridge.cs:66-121,468-483`).
- **Assessment:** Risk. It is simpler and avoids 2s file-polling latency, but it needs a network path from the container to the host, which network_mode: none and Linux compose do not provide. Binding every interface also leaves security resting on the token.

### Registry and type-name matching

- **Python:** @sandboxenv decorator, exact-name lookup, lazy entry-point loading and install hints (`py:src/inspect_ai/util/_sandbox/registry.py:24-84`; `py:src/inspect_ai/_util/registry.py:319-326`).
- **C#:** A static case-insensitive dictionary, an explicit Register call, and an error listing the known types; ResolveSpec compares types case-insensitively (`cs:src/InspectAzureAI.Eval/Sandbox/SandboxRegistry.cs:15-47`; `cs:src/InspectAzureAI.Eval/Runner/SandboxSetup.cs:33`).
- **Assessment:** Fine as a .NET idiom. The risk is extensibility rather than correctness: the CLI has no way to load a provider from another assembly.

### How cleanup and init failures are reported

- **Python:** A sample cleanup exception becomes the sample's error, which can be retried. A task_init failure aborts the whole run. task_cleanup errors are logged as warnings (`py:src/inspect_ai/_eval/task/run.py:2860-2861`; `py:src/inspect_ai/_eval/run.py:205-207,1060-1070`).
- **C#:** A cleanup exception is only an ErrorEvent and the sample keeps its score. An init failure produces that task's Error log (exit 1). Task-cleanup failures go only to the optional reporter (`cs:src/InspectAzureAI.Eval/Runner/SampleRunner.cs:250-263`; `cs:src/InspectAzureAI.Eval/Runner/Eval.cs:230-251`).
- **Assessment:** Mixed. Isolating init failures per task suits eval-set. But swallowing cleanup and task-cleanup failures, silently when no reporter is set, hides leaked containers.

### Choosing the default compose service

- **Python:** The running x-default service, else 'default', else an error (`py:src/inspect_ai/util/_sandbox/docker/docker.py:236-263`).
- **C#:** The same, plus a lone service with any name becomes the default. The 'default service is not running' branch at lines 129-133 can never be reached, because every candidate comes from running environments (`cs:src/InspectAzureAI.Eval/Sandbox/Docker/Compose/DockerComposeSandbox.cs:116-133`).
- **Assessment:** Fine. The leniency is documented, though a compose file written against C# may fail in Python. The dead branch should be removed, since the reliability table mistook it for real handling.

### Where tool-support artifacts come from

- **Python:** Bundled binaries first, then S3 with retries (a digest mismatch only warns unless strict mode is on), then a local PyInstaller build (`py:src/inspect_ai/tool/_sandbox_tools_utils/sandbox.py:280-486`).
- **C#:** A user cache or INSPECT_SANDBOX_TOOLS_BINARIES_DIR, then a single S3 GET with digests always enforced; 403/404 becomes a PrerequisiteError (`cs:src/InspectAzureAI.Eval/Tools/Support/SandboxToolsBinary.cs:154-268`).
- **Assessment:** Fine for security, thanks to strict digests and a verified cache. The reliability risk is that the first injection needs S3, and one transient S3 error fails it because there is no retry.

### Ctrl+C handling

- **Python:** KeyboardInterrupt/CancelledError. Interrupted samples are left for a shielded cleanup at run end, and the process exits 130 (`py:src/inspect_ai/_util/error.py:96-104`; `py:src/inspect_ai/_eval/run.py:1060-1070`).
- **C#:** CancelKeyPress sets e.Cancel on every press and cancels a token. Each sample tears down inline with CancellationToken.None, the log is marked Cancelled, and the process exits 3 (`cs:src/InspectAzureAI.Cli/Program.cs:8-12`; `cs:src/InspectAzureAI.Eval/Runner/Eval.cs:227-229`).
- **Assessment:** Mostly fine, because containers are removed. The risks are that a second Ctrl+C cannot force an exit if docker hangs during teardown, and scripts checking for exit 130 will see 3.

### Sandbox specs recorded in the log

- **Python:** EvalSample.sandbox is the sample's own spec (null when only the task sets one), and EvalSpec's config path is made cwd-relative (`py:src/inspect_ai/_eval/task/run.py:3117`; `py:src/inspect_ai/_eval/task/log.py:190-194`).
- **C#:** EvalSample.Sandbox is the resolved task-or-sample spec, EvalSpec stores the config as given, and object configs are rejected when a log is read (`cs:src/InspectAzureAI.Eval/Runner/SampleRunner.cs:274`; `cs:src/InspectAzureAI.Eval/Runner/Eval.cs:149`).
- **Assessment:** Low risk. Tools comparing Python and C# logs will see different sample-level sandbox fields, and C# cannot read Python logs that contain object configs.

### Output limits

- **Python:** INSPECT_SANDBOX_MAX\_\* is read once per task into ContextVars (positive integers only). Scoped override context managers exist, and the proxy enforces the exec cap for any provider (`py:src/inspect_ai/util/_sandbox/limits.py:61-196`; `py:src/inspect_ai/util/_sandbox/events.py:115-138`).

- **Assessment:** Minor risk. The built-in providers trim correctly, but a registered third-party provider can return unbounded output, and sandbox_service rejects 10-150 MiB requests that Python accepts.

### Local provider details

- **Python:** A missing executable raises FileNotFoundError. Under --no-sandbox-cleanup the directory is left to TemporaryDirectory's finalizer. Local exec takes a slot in the subprocess limiter, and the provider sets the sandbox-tools dir env and stops the tools server on cleanup (`py:src/inspect_ai/util/_sandbox/local.py:45-128`).
- **C#:** A missing executable returns exit 127. The directory is kept when cleanup is off. - **Assessment:** Fine for exit 127 and keeping the directory, both of which follow documented contracts. Minor risk: sandbox-tools injected into a local sandbox land at a fixed absolute path outside the sample directory and are never stopped.

## Method

- Workflow run `wf_690bb089-cdc` (14 agents). The work was split into six subsystems. For each, one agent read both codebases and filled a feature-by-feature table, then a verifier tried to refute every non-parity row by searching the C# tree under other names, and spot-checked at least half of the parity rows for matching semantics.
